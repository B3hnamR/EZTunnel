# Security model

## Builds And Updates

Source builds run directly. The built-in updater accepts only cryptographically
verified official files, authenticating bytes before executing a candidate. Custom builds can be installed through the explicit local
installer without starting services. No private signing keys are required to
build or test the application.

Version 0.9.0 introduced the current protocol. Both endpoints must update together;
see [the protocol contract](protocol.md). Wire 1..3 are configuration choices within
it, not compatibility switches for older versions. Official release signing is a
separate, controlled workflow; this checkout includes only public update verification.


Both servers of a tunnel hold the same tunnel key: 24 random symbols (120 bits) and a check symbol. The server's and the client's Noise identities are derived from it, the client pins the server identity and the server accepts only the client identity. Noise IK authenticates and encrypts records using X25519, ChaCha20-Poly1305, and BLAKE2s. With `tls_auto`, TLS carriers present a certificate derived from the same key and the dialing side accepts exactly that certificate; otherwise they verify certificates and server names in the usual way. No insecure-certificate switch is provided.

Anyone who has the tunnel key can act as either server, so treat it like a password: the manager stores it only in `/etc/eztunnel/tunnels/NAME.json`, readable only by root and the service account, and the program refuses to load a file with a key that other users can read. Someone who records a handshake cannot test guesses faster than the key's 120 bits allow. To change a key, create the tunnel again on both servers. Separate key files (`private_key_file`, `peer_public_keys`) remain supported for setups that want a different identity per server.

No application code contacts an external API, identity server, or telemetry service. It does not download another executable. Normal network access consists of configured tunnel peers and authorized target traffic, including ordinary system DNS lookup for hostnames. Installing Rust dependencies from source still uses the usual package registry unless dependencies are already cached.

Tools → Export all tunnels writes every tunnel configuration, tunnel keys included, to one file that only its owner can read; treat it like the keys themselves and delete it after use. Tunnel keys, private Noise identities and TLS private keys stay local and must not be committed or put in release archives. Generated private files use Unix mode 0600 and are never overwritten. Copy the tunnel key (or public keys and trust certificates) between servers over a trusted channel such as SSH. The manager runs each tunnel as the unprivileged `eztunnel` account with only the capabilities it needs (binding ports below 1024, raw sockets, or creating a TUN device).

In forwarding mode, `allowed_targets` compares requested strings, not resolved IPs or CIDR ranges: `host:port` must match (host names ignore letter case, as DNS does), `host:*` allows every port of that host text, and `*` allows anything. `localhost:8080` differs from `127.0.0.1:8080`. The manager's default on the foreign server is `127.0.0.1:*`: the Iran server can reach only services on the foreign server itself. DNS names may resolve differently over time. An empty allowlist denies access; `"*"` grants access to any target the client can reach. A compromised authorized server can request any allowed destination. In TUN mode, Linux routes and firewall rules govern ordinary IP packet access. When `tun.forwarding_port` is enabled, its additional authenticated TCP/SOCKS relay enforces the forwarding allowlist; that allowlist does not restrict ordinary IP packets carried by the TUN.

The speed test (Manage tunnels → Speed test) opens streams to a reserved target, `down.N.speedtest.eztunnel.invalid:9` or `up.N...`, that the client side answers itself without consulting `allowed_targets`. Names under `.invalid` never resolve on the internet, so nothing legitimate uses them: the SOCKS5 listener refuses them and the configuration refuses them as map targets, so users cannot reach the speed test responder. Only the manager can start a speed test, through the tunnel's control socket (`/run/eztunnel-NAME/control.sock`, readable only by the tunnel's account and root). It serves at most 16 requests at once (a client over that limit is told so at once) and lets a client that does not send its request line go after 5 seconds, so a stuck local script cannot hold descriptors for ever; a speed test request with a number of the wrong type (`"bytes":"100"`) is refused instead of running with a default.

**TLS look (`tls_profile`).** With `chrome`, the dialing side of a TLS carrier sends the ClientHello of Chrome (built by BoringSSL, the library Chrome uses), so JA3/JA4-style fingerprinting of the handshake sees a browser instead of a Rust program. This is a look, not a protection: the encryption and the pinned certificate are unchanged, the server's reply (ServerHello, certificate), the packet timing and the traffic inside are not made to resemble a website, and Chrome and Edge are the only browsers that can be imitated. Whether a given network treats the two differently cannot be known in advance; test it on the link. The Chrome path trusts the same identity as the classic one, through a different check: with `tls_auto` it pins the public key of the key-derived ECDSA certificate (the classic path pins the Ed25519 one; both come from the same tunnel key); with `ca_file` it trusts only that file; with neither it uses the system's trusted roots (the classic path uses a bundled list).

**Probe resistance (wire version 2).** A tunnel with `wire_version: 2` hides the fixed patterns a filter or prober could use to recognise a server. Plain TCP, KCP and FEC streams start with a random-length run of printable characters (nonce, pad length, padding) and are masked after it (keyed from the server's public key), so the first packet has no fixed length and no fixed value. The printable start is deliberate: a stream that was uniformly random from the first byte was cut by the Iranian network used for testing. A connection that fails the handshake is read and ignored for a random time (`stealth.probe_hold_sec`, ending at `timeouts.handshake_sec` at the latest) before it is closed. A wrong HTTP or WebSocket request gets an ordinary web-server 404 page (with a `Date` header, and the connection is closed afterwards like a server that said `Connection: close`); a plain-text HTTP request sent to a TLS carrier (`wss`, `https`, `xhttps`) gets the 400 page nginx gives for that ("The plain HTTP request was sent to HTTPS port"), not a silent close. The Upgrade token, XHTTP header names, default path, default User-Agent and the name inside the derived certificate come from the server key instead of project names. This defends against fingerprints and cheap active probes. It is not protection against traffic analysis (packet sizes and timing of bulk data still show), and the mask is not encryption: the Noise session inside still provides secrecy and authentication. `stealth.record_pad_max` pads every record by a random amount and `stealth.jitter_ms` delays the first record of each burst, which blunts size and timing analysis of small and sporadic traffic; neither hides the volume and rhythm of bulk transfers, and they cost bandwidth and a little latency, so they are off by default. Version 1 (the default for existing tunnels) keeps the old, recognisable format. Raw `tun` carriers, `fec-raw` packet shapes and the `fec-udp` knock port are not covered.

Port maps and SOCKS have no additional user authentication. A SOCKS5 UDP relay answers only the host that opened the association, and only from the port of its first datagram, and ends when the client's TCP connection closes; its destinations go through the same `allowed_targets` and reserved-name checks as CONNECT. Keep their listeners on loopback or apply firewall and destination-service authentication. Authorize only client identities appropriate for the server's shared forwarding setup. Public-key authorization does not assign separate destination namespaces to clients.

`fec-raw` uses raw packet layouts and KCP/FEC; `fec-udp` uses UDP KCP/FEC; direct raw TUN preserves unreliable IP delivery. Raw TUN uses a bounded replay window and explicit authenticated nonces so reordering and loss do not force ordered delivery. HTTP/WebSocket/TCP camouflage provides no promise of indistinguishability, censorship resistance, or evasion. The project has functional tests but has not undergone an independent cryptographic or penetration audit.

Raw carriers need `CAP_NET_RAW`; creating a TUN interface needs `CAP_NET_ADMIN`. Raw receive paths check the Ethernet destination, the IPv4 source address (the configured `raw.peer_ip`, unless address spoofing is configured, in which case the outer addresses are intentionally not predictable) and the packet lengths and checksums before processing authenticated payloads. IP spoof and proto58 mode settings control outer headers locally; they add no external identity or verification dependency. XHTTP request/session/body limits bound HTTP resource use, and TLS verification stays enabled for all edge attempts.

Connections that have not finished the key handshake wait in a separate pool (`max_pending_handshakes`, `max_pending_per_ip`) and take a session slot (`max_connections`) only after they authenticate, so unauthenticated connections cannot lock out the real peer. Accept loops back off and retry on temporary errors such as running out of file descriptors; only a run of 120 failures in a row (about two minutes) ends the listener, and the service manager then restarts the tunnel. The first Noise message of a handshake can be replayed by anyone who recorded it, and the replay gets an answer. So a side that accepted a connection (the listening server, or the server that dials in `server_dials` mode) trusts the session only after the peer has sent a record that decrypts under the session keys, which a replay cannot do: until then the session is not in the pool users are sent to, is not logged as authenticated, and does not replace a running TUN session. If nothing arrives within `timeouts.handshake_sec` the connection is dropped. The streams of a session (`max_streams`) are shared by all maps; the per-address limit and the idle timeout above keep one address from using them all. Public maps are limited per source address (`max_streams_per_ip`, default 512, enforced once the sessions are three quarters full, so shared addresses can still use the room that is there) and idle forwarded connections are closed (`timeouts.tcp_idle_sec`, default one hour), so one address cannot hold every stream slot; XHTTP sessions (`xhttp.max_sessions_per_ip`) and FEC conversations (`fec.max_peers_per_ip`) can be limited per address too. TLS private key files that every user of the machine can read are refused. The strongest protection for a two-server tunnel is still to firewall the tunnel port to the other server's address.

The program stops cleanly on SIGTERM (the signal `systemctl stop` sends) as well as Ctrl-C. TLS certificate and key files are read once and reused; if they change on disk (for example after a certificate renewal) the new ones are used for new connections without a restart, and if they cannot be read at that moment the previous ones stay in use.

The plain `kcp` carrier runs over UDP, which has no handshake: the first datagram from an unknown address starts a session, and a datagram that claims to come from a peer's address can disturb that peer's session (data stays encrypted and authenticated, but the link can be reset). The listener bounds sessions (`kcp.max_sessions`, `kcp.max_sessions_per_ip`) and logs junk datagrams only at debug level. Expose the `kcp` port only to your other server (firewall it to that address); `fec-udp` adds a knock port but no real source authentication either.

The `fec-udp` knock is not authentication: it is a one-byte request and answer on a second UDP port that only filters stray traffic, and a forged source address can pass it. The real protection is the key handshake that follows. Likewise the checksum embedded in the `.run` installer detects a damaged download, not a tampered one; compare the installer against a `SHA256SUMS` file obtained through a separate trusted channel.
